5/41

Asymmetric key systems

What if the keys are not the same, and we use public/secret keys?

p_{k} is the public key for Bob, s_{k} is his private key. Only Bob can decrypt a message sent to him, but anyone can encrypt it.

Participants each have private and public keys, and the keys cannot be derived from each other.

6/41

Asymmetric encryption and authentication
A model for public/private keys, key rings, many keys...

To the left we see Bob encrypting a message to Alice, using Alice's public key. which he keeps on a key ring. Only Alice can decrypt it.

To the right we see Bob sending a message that only he could have sent. He uses his own secret key. Anyone can decrypt it, but only Bob could have sent it.

7/41

Doing both encryption and authentication...
Possible and actual techniques...

The technique at the left involves two asymmetric encryptions, and is considered too slow. Instead we hash the encrypted message and encrypt that (much smaller, so faster) hash, to append as a signature for the message.

This is what a digital signature is, an encrypted hash, of a file or something. The originator uses their secret key, and anyone who knows the matching public key can check it against the hash of the file.

#1: Key Agreement (Diffie (Whitfield)/(Martin) Hellman)[1,ctrl-i2,ctrl-i6]

After exchange, knowledge is different...
As explained by Prof Kenochi, the participants exchange the results of calculations. At the end, Alice and Bob can both calculate a new key.
Someone listening in however, is unable to calculate the key, unless they are able to solve a computationally complex problem. Each of the participants has a different set of things they know, but only Alice and Bob can compute g^{ab}\bmod p .
11/41

The construction for Diffie-Hellman KA

Concrete: what do the parties do?(modulo math)

Alice and Bob pre-determine a choice of p, and a generator g. The protocol is:

  1. Alice, Bob choose uniform values a,b from \mathbb{Z}_{p}^{*} and exchange h_{A}=g^{a}\bmod p, h_{B}=g^{b}\bmod p.
  2. Alice computes the secret:

    \boldsymbol{k_{A}=(g^{b}\bmod p)^{a}\bmod p=(g^{b})^{a}\bmod p}

  3. Bob computes the secret:

    \boldsymbol{k_{B}=(g^{a}\bmod p)^{b}\bmod p=(g^{a})^{b}\bmod p}

Shared key is:

\boldsymbol{k_{A}=k_{B}=(g^{b})^{a}\bmod p=(g^{a})^{b}\bmod p=g^{ab}\bmod p}

Abstract: what do the parties do?(\times cyclic group)

Alice and Bob pre-determine the choice of group {\cal G} and a generator g. The protocol is:

  1. Alice, Bob choose uniform values a,b from {\cal G} and exchange h_{a}=g^{a}, h_{b}=g^{b}.
  2. Alice computes the secret:

    k_{A}=h_{b}^{a}

  3. Bob computes the secret:

    k_{B}=h_{a}^{b}

Note that k_{A}=k_{B}=g^{ab}. A common choice of group (as above) is {\cal G}=\mathbb{Z}_{p}^{*}.

Why use ECC?

ECC has an embedded OWF problem

ECC addition is an analog of modulo multiply, so repeated addition is like modulo exponentiation.

We have a “hard” problem, equivalent to the discrete log problem. Consider Q=kP, where Q,P belong to a prime curve... it is

  • “easy” to compute Q given k,P but
  • “hard” to find k given Q,P.

This is known as the elliptic curve logarithm problem.

Best attack on ECC so far is Pollard-rho/Floyd!

Want to find k:kP=Q? Cast it as a collision!

The world is a chain of elements of the group, partitioned into three (S_{1},S_{2},S_{3}) types (coloured). We either double the element, or add P or Q:

{\begin{array}{lll} P_{i+1}=f(P_{i}) & = & \left\{ \begin{array}{lll} P_{i}+P & \mathrm{if} & P_{i}\in S_{1}\\ 2P_{i} & \mathrm{if} & P_{i}\in S_{2}\\ P_{i}+Q & \mathrm{if} & P_{i}\in S_{3} \end{array}\right.\end{array}}

Each P_{i} is some sum aP+bQ. On collision, a_{1}P+b_{1}Q=a_{2}P+b_{2}Q, and

{\begin{array}{lll} \frac{a_{1}-a_{2}}{b_{2}-b_{1}}P & = & Q\end{array}}

20/41

Summary...

What we just saw were examples based on OWF

We saw three systems where we used operations that are easy to do one way, say of {\cal O}(k), and difficult to reverse and do the other way: perhaps {\cal O}(e^{k}), the one-way functions.

The Diffie-Hellman key agreement scheme relied on the difficulty of calculating discrete logs. RSA encryption relied on the difficulty of factorization, and ECC relies on the elliptic curve log problem.

In each case, we want our mathematical systems to be of fixed size (i.e. modulo), and to operate over all values. A suitable mathematical structure is to use finite cyclic groups, or fields and if you have an interest in cryptography, there is a lot to learn in this area.

MD5 and SHA[ctrl-i4]

MD5...

Was designed in 1991 by Ron Rivest (of RSA fame), as a cryptographic hash function. However it has been found to not be collision-resistant (see [i4] above), and so, despite extensive use in industry today, it should no longer be used as a cryptographic hash.

The SHA family...

Originally designed by NIST in 1993 (SHA-0) but revised in 1995 as SHA-1. Revisions in 2002 led to SHA-2 256/384/512: higher security levels, and with no known weaknesses. SHA-3 was released in 2012 - it is the newest one, with some different design elements.

Cryptographic hashes

A hash is not just a checksum

A cryptographic hash meets extra security requirements. In particular, we want them to be collision resistant (defined on next slide).

A cryptographic hash is an important crypto primitive. It is used in digital signatures : hash-and-sign, protecting password files (with salted hashes), Commitment schemes, Proof-of-Work in Bitcoin, IPV6 cryptographic addresses, and so on.

25/41

Properties of cryptographic hash functions

Desirable properties: It should be efficient, public, and...
  1. It should be computationally infeasible to find two items x,x' where x\neq x', but both map to y={\cal H}(x)={\cal H}(x') (collision-resistant).
  2. Given x, it should be computationally infeasible to find an x'\neq x such that {\cal H}(x')={\cal H}(x) (target-collision, or second pre-image resistant).
  3. Given y, it should be computationally infeasible to find item x mapping to it: y={\cal H}(x) (one-way property, or pre-image resistant).

Note that (1) implies (2), and also a (2) attack implies a (1) attack.

When two messages map to same hash...
  1. Can there be no collisions at all? If the number of messages \#m is greater than the number of hashes \#{\cal H}(\ldots), we have the pigeonhole principle - if there are n roosts for n+1 pigeons...
  2. How likely are collisions? Consider the birthday paradox1. What is the probability that at least two of N randomly selected people have the same birthday? It is much more likely than you would suspect...
  • 1 BTW - It is not really a paradox, just counter-intuitive.

The Birthday “Paradox” is not a paradox

It is NOT the likelihood that someone shares a specific person's birthday. It is the likelihood that amongst every pair of candidates there will be (at least) one matching pair. This turns out to be quite likely - even here: for N=23 , this likelihood is about 0.5 .
We can attack some digital signatures using an attack based on the birthday paradox.
Likelihood versus number of random choices

In general, in a birthday attack over n items, to achieve a probability of p, we should choose about \sqrt{2n\ln\frac{1}{1-p}} items. In the above, for n=365,p=0.5 we have about 1.177\sqrt{365}\thickapprox22.5. This value (1.177) gives rise to the common approximation we use: take the square root2.

  • 2 For n\mhyphen\mathrm{bit} attack, only need 2^{\frac{n}{2}} values to get 50% chance of success.

The birthday attack - straightforward method

Find x,x’ s.t. {\cal H}(x)={\cal H}(x’); time {\cal O}(2^{n}), memory {\cal O}(2^{n})...

The birthday attack can be used to speedup the search for a hash collision with a “square-root” reduction.

Suppose a digest is n bits, and we have a random set of around 2^{\frac{n}{2}} messages (by the birthday attack, the chance of having a collision is around 0.5 probability). A straightforward implementation of a birthday attack stores this set in the memory and then searches for a collision. However, in practice, the memory requirement is more difficult to meet compared to the running time requirement. Imagine if n=80 bits, then there are 2^{40} pairs of messages and digests. Assuming each pair take up 32 bytes, then the total storage is 2^{45} bytes, i.e. 32TB. Nevertheless, 2^{40} hash operations can be done in reasonable time.

The following improved birthday attack takes about twice the time, compared to the straightforward implementation, but uses constant memory.

Floyd - for chains like x_{0}\rightarrow f(x_{0})\rightarrow f(f(x_{0}))\rightarrow\ldots

Find loop with f(x)\myeq{\cal H}(x); time {\cal O}(2^{n}), and memory {\cal O}(1)

(Robert W.) Floyd's cycle-detection algorithm: the Tortoise t and the Hare h. Variables hop through a graph at different rates, stopping when they collide.

Algorithm: part 1 finds the loop in a (digest/hash) chain
def H(x):
   return md5(x.encode('utf-8')).hexdigest()
def f(x):
   return H(x)[:10]

def floyd(x0):
   t = f(x0)
   h = f(f(x0))
   print('Find the loop')
   while (t != h):
      t = f(t)
      h = f(f(h))
35/41

Floyd - for chains like x_{0}\rightarrow f(x_{0})\rightarrow f(f(x_{0}))\rightarrow\ldots

Algorithm: part 2 finds the collision
   t = x0
   print('Find the collision'
   while (t != h):
      if (f(t) == f(h)):
         break
      t = f(t)
      h = f(h)
      if (t != h):
         temp_t = t
         temp_h = h
         pass
   return temp_t,temp_h

This reruns, but just one step at a time. The tortoise restarts at the beginning, and the hare at the result of part 1. They meet at the beginning of the loop (where the collision is).
