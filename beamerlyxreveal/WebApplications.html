Accessing an embedded system

Injection #1: The page allows a command injection into the system

The actual command to mount the remote file system for the camera will be:

smbmount //192.168.0.5/toto /mnt -o username=toto,password=PASS

The trick here is to replace the password PASS with something like “PASS;/bin/command”. After mounting the drive, your command will be executed (it can be anything, but should be something to get you extra access).

A web application injection...

It is common to link pages to database servers

In this scenario, the web server queries a local database server based on a client query. In the example, the client wants to look for records associated with the userName string “hugh”.

10/44

The system architecture seems innocuous, but... (SQLi)[i8]

You access a remote web site, and fill in a form asking for particular information from a database. For example - getting information on a particular user, or a particular product.

Unfortunately, sometimes it is possible to craft a substring containing SQL commands that can do different things from what the developer of the web site intended. As a result...

Technique of crafting special substrings with SQL commands is called the “SQL injection attack”.

11/44

The result is BAD...

We end up with this:

The attacker makes up a userName string which has extra stuff in it. This extra stuff may do something malicious when it gets to the database server.

12/44

Detail on the injection...

userName web form input is given to a SQL command
SELECT * FROM users WHERE name = '" + userName + "';

If the user types in (say) hugh, then you get

SELECT * FROM users WHERE name = 'hugh';

A malicious user could type in (say)

a';DROP TABLE users;SELECT * FROM info WHERE 't' = 't

And then you get:

SELECT * FROM users WHERE name = 'a';
DROP TABLE users;
SELECT * FROM info WHERE 't' = 't';

Please dont do this! It is aggressive and nasty.

Java: control over inputs

Java: Injection from getParameter()

Java Code in a web page for accessing SQL database:

String Matric = request.getParameter("matric");
...
String sel = "SELECT  marks  FROM test.mrks
              WHERE userName= '" + Matric +  "'";
Statement stmnt = connection.createStatement ();
ResultSet resultSet = stmnt.executeQuery(sel);
...
We can use similar ideas from the PHP ones:

Use Java methods to sanitize input (like mysql_real_escape_string()). Java also has a PreparedStatement class (instead of the Statement class above). Parameters passed in have TYPE (i.e. integer, float..). A PreparedStatement does not automatically stop SQL injections, but it allows you to control the constructed SQL strings more precisely. You may still need to filter the parameters (if for example the parameter was a string).

Too many privileges? Also a problem...

Base scenario - as before - a web server with SQL access:

PHP code in a web page for accessing SQL database:

$con = mysql_connect('...','root','rootpasswd') ...

Instead should be:

$con = mysql_connect('...','nobody','nobodypasswd') ...
Why?

Consider the situation where someone succeeds with an injection, or with XSS attack, or with some combination. In the two cases:

  • With root access, the attacker could cause significant damage to the database - perhaps removing the database entirely (using the SQL “DROP TABLE” command).
  • Without root access, i.e. only enough access to perform the required task, a successful attacker is limited in the damage that could be done.

Note that the nobody user might only be allowed to read and write entries, not create new ones, or delete ones, or delete tables, and so on.

Control over outputs[X]

Why is it needed? In short, persistent XSS

Consider the situation where someone has uploaded some HTML. You may want to display this HTML with rich text (i.e. formatting). However, they may have included some malicious (javascript or other) code in their HTML.

Your task then is to take the HTML provided, and output HTML without extra stuff. You are to sanitize the HTML. To do this effectively, there are no real shortcuts: it is best to use a library intended for this purpose. For PHP for example at [X] above.

Turn badhtml into goodhtml!

What is pentesting?

The complexity of modern (distributed) systems is a security weakness

Defences should start while the system is being dreamed up - we use secure technologies, secure development techniques, secure integration and deployment. But despite the best laid plans, the systems still must be continually tested, and risk-assessed/monitored.

Let us start with Wikipedia’s view:

A penetration test, colloquially known as a pentest or ethical hacking, is an authorized simulated cyberattack on a computer system, performed to evaluate the security of the system...

The test is performed to identify weaknesses (or vulnerabilities), including the potential for unauthorized parties to gain access to the system's features and data, as well as strengths, enabling a full risk assessment to be completed.

Red and blue teams

Blue teams are visible, but it may be the case that red pen-testing teams may be deployed - in these cases, no-one in the IT department knows about them!

It is needed, and is NOT hacking!

(OWASP)

Pen-testing \neq hacking(Pen-testers are your friends)

Security hackers are people skilled in IT who use non-standard means (bugs/errors) to break into computer systems and access data which would otherwise be inaccessible to them.

By contrast pen-testing is a professional activity where authorized teams, paid for by the target companies, evaluate the security of a precisely scoped-out system. In order to do this, they may very well use hacking. In the end they help you remediate issues.

Pen-testers follow these steps

Extra steps than “hacking” and a different focus

Pen-testers discuss the scope with the client first, and also report back on what they found, and best practices for remediation. In a recent pen-test project here at SoC, only about 25% of the time spent was direct hacking activities.

Summary: Web Applications

Today, we have seen...

Servers trusting browsers - We saw a range of injections, where servers placed too much trust in the client (the browser), and as a result, malicious activities happened. We saw command and SQLi (SQL injections), and then how programmatically we can defend the servers, by ensuring that the input from the client/browser was sanitised.

Browsers trusting servers - We saw a range of XSS (Cross Site Scripting) attacks, where browsers/clients placed too much trust in the server, and as a result, malicious activities happened. We saw reflected and stored XSS, CSRF and clickjacking, and then how programmatically we can defend the servers, by ensuring that not only the input from the client/browser was sanitised, but also the output from the server.

Pen-testing - Organisations should consider hiring a pen-testing company. They use a range of techniques to help remediate security issues in applications.
